\section{Project Specification}

\subsection{Problem Statement}
Industrial IoT systems are made up of many sensors, actuators, and communication tools that must work well together in real time.In reality, these parts usually don't share the same standards.Each sensor might use a different type of connection, each actuator might expect a different control signal, and each system might use a different way to send information.Putting all these parts together into one working system is a big challenge, and it becomes harder as more devices are added.

In this situation, BWS faced a common problem.
For every project, the company created custom software that was suited only to that specific setup.Every time new parts were added, the system had to be reconfigured and the software had to be rebuilt almost from scratch.Because this software was tightly connected to the hardware of each project, very little of it could be reused for the next one.As a result, engineers had to redo similar tasks again and again, adapting them to small changes in the hardware.

This way of working was costly and time-consuming.
Each new project started from scratch instead of building on previous work, which slowed down development.There was no reuse of work between projects, so engineers kept doing the same tasks over and over, and the knowledge from one project didn't help with the next.Keeping things running was also hard because even a small change in the hardware required updating, testing, and rechecking the software, which increased the chance of mistakes and the time needed to keep the system working.This was made even worse by the wide variety of communication standards used in industrial settings, such as RS485 with Modbus, CAN, LIN, and I2C or SPI buses.Solving each problem with a unique, custom solution made development harder and the systems more complex to extend and scale.

To fix these issues, BWS started the IOBOX project.
The goal was to create a flexible, hardware-independent platform that could support many different setups using a single, shared software base.Instead of rebuilding the system for each project, the idea was to build an architecture where parts that depend on specific hardware are separated from the core functionality.This way, changing to new hardware only requires minor adjustments instead of a complete rewrite.The IOBOX aims to make adding a new device into the system a simple configuration task instead of a full rebuild.

This change has a big effect beyond just fixing a technical problem.
It changes how the company uses and keeps its engineering effort.In the old way, each project used resources that only worked for that project, and this effort was lost once the work was done.A common platform, however, adds value over time—every improvement or new part added to the IOBOX helps not just the current project but all future projects.This turns repeated, short-term effort into a lasting, growing asset.

This has a direct effect on how development costs and time work.
Because each new deployment is mainly about setting things up, the time it takes to turn a client request into a working system is greatly reduced.This helps the company be faster in delivering solutions, which is important in this field.Also, writing less hardware-specific code reduces development costs and lets skilled engineers focus on more important tasks instead of re-doing basic functions.The platform also has a strong impact on quality because the same, improving software is used in many projects, making its key parts more tested and reliable over time.This makes it easier to maintain the system because hardware-related code is separated into clear sections, so any changes or problems only affect a limited part of the system.

On a bigger level, the IOBOX helps the company grow and serve more different uses with the same core technology.
It supports many types of sensors, actuators, and industrial communication standards, so different applications like environmental monitoring, energy tracking, process control, and equipment management can all use one platform instead of many separate solutions.The most important effect of this project is structural—it replaces a way of working that is split into individual projects with a single, reusable engineering base.This makes it faster and more efficient to build better industrial IoT solutions that are more reliable and cheaper to develop.
\section{Presentation of the IOBOX Platform}

The IOBOX is an industrial flexible system that helps to interconnect sensors, actuators and communication tools in industrial environments.

It adopts a modular approach that distinguishes the parts dependent on specific hardware from the parts that manage the main functions.
This is achieved through specific software tools such as drivers, a board support package, and Manager, which facilitate use in different systems and maintain an easy update.

The IOBOX can interface with various types of industrial equipment such as analog and digital inputs and outputs, communication ports and measurement devices.
Its software configuration can be adapted to various industrial requirements without major changes in the firmware.

By connecting the hardware and the software in a straightforward way, the IOBOX simplifies the assembly and the use in industrial environments.

\subsection{Project Objectives}

The key objective of this project is to develop the IOBOX platform which will collect, handle, control, and transmit data in real-time.

To be more specific, the project aims to:
\begin{itemize}
    \item Developing a scalable framework that is capable of acquiring the data and controlling it according to industry needs.
    \item Provide a unified software abstraction layer for heterogeneous peripherals.
    \item Delivering programmable analogue and digital input-output features.
    \item Supporting industrial communication protocols such as Modbus RTU via RS485, CAN, LIN, and multi-channel UART, ensuring the compatibility with other industrial devices.
    \item Develop a modular software architecture based on abstraction layers and reusable software components.
    \item Design the software architecture to allow new sensors, actuators, and communication interfaces to be added with minimal modification to the existing code.
\end{itemize}

The resulting platform will lower development costs and reduce time-to-market by offering a reusable embedded architecture that adapts to various industrial settings.

\subsection{Development Methodology}
The project development was based on the V-Model approach, a systematic development framework widely used in embedded and industrial applications in order to preserve traceability throughout the system's lifecycle pairing each development stage with a matching validation phase.

The project activities were organized according to the different phases of the V-Model in which the requirements-gathering phase focused on identifying the platform capabilities and technical constraints required by BWS. These requirements formed the basis for the system architecture that was designed, including the definition of the four-layer software structure and the selection of the hardware components.
The detailed design stage then focused on the BSP modules, communication manager and sensor drivers.

After the design work was completed, the implementation phase involved coding BSP drivers, sensor management systems, communication protocols, and application-level functionalities. The project's validation included testing each BSP module individually, verifying sensor data acquisition and Modbus communication in an integrated environment, and performing complete system-wide testing to confirm that all operational requirements were met.

\section{State of the Art}
 
The acquisition, processing, and control of data in industrial environments is a
well-established field, and several categories of solutions already address parts
of this problem. Reviewing them helps to situate the IOBOX platform and to clarify
the specific need it is intended to fulfil.
 
% -------------------------------------------------------------------------
\subsection{Commercial Industrial I/O Modules and PLCs}
% -------------------------------------------------------------------------
 
The first category consists of commercial industrial input/output modules and
programmable logic controllers (PLCs), such as those offered by manufacturers like
Siemens, Schneider Electric, WAGO, and Beckhoff. A representative example is the
\textbf{Advantech ADAM-6017} \cite{advantech_adam}, a widely used Ethernet-based
analog input module that provides multiple analog channels and digital I/O with
support for standard industrial protocols. These devices are mature, robust, and
often certified for demanding industrial conditions, and they support a range of
standard protocols. However, they are typically proprietary and closed systems:
their firmware cannot be freely modified or extended, they involve significant unit
and licensing costs, and they cannot be deeply integrated into a company's own
software ecosystem. For an organization that needs to tailor and extend the
platform to its own evolving solutions, this lack of openness is a considerable
limitation.

\subsection{Generic Embedded Development Platforms}
% -------------------------------------------------------------------------
 
The second category comprises generic embedded development platforms, ranging from
Arduino-based boards and single-board computers such as the Raspberry Pi to
microcontroller platforms based on the ESP32. A notable industrial-oriented example
is the \textbf{Arduino Opta} \cite{arduino_opta}, a micro-PLC that brings the open
Arduino ecosystem into an industrial form factor with relays and analog inputs.
These solutions are flexible, low-cost, and open, which makes them attractive for
prototyping. Nevertheless, they are generally not designed for full industrial
robustness, and they often lack the analog precision and the native fieldbus
support, such as CAN~FD or hardware-assisted RS485 and Modbus, required in
industrial settings. More importantly, they provide no ready-made, reusable
software architecture: the entire firmware structure still has to be developed for
each application, which reproduces the very problem this project seeks to eliminate.

% -------------------------------------------------------------------------
\subsection{In-House Custom Firmware}
% -------------------------------------------------------------------------
 
The third category is the custom, in-house firmware approach previously adopted by
BWS, in which dedicated software was developed for each individual deployment. While
this approach offers full control and a close fit to each project, it is inherently
non-reusable, as discussed in the problem statement, and leads to duplicated effort,
slower development, and difficult maintenance.
 
% -------------------------------------------------------------------------
\subsection{Positioning of the IOBOX}
% -------------------------------------------------------------------------
The IOBOX platform is positioned deliberately between these categories. It combines
the openness, low cost, and full customizability of an embedded platform with a
reusable, layered, and industrial-grade software architecture that the company fully
owns and can extend. Unlike closed commercial modules, it can be freely adapted and
integrated into BWS's own ecosystem without licensing constraints; unlike generic
development boards, it provides genuine industrial connectivity and a structured,
reusable firmware base; and unlike the previous in-house approach, it replaces
per-project redevelopment with a single, configurable foundation. It is this
combination of flexibility, industrial capability, and reusability that motivates
the development of a dedicated platform rather than the adoption of an existing
solution.
